VUE D'ENSEMBLE

Architecture de formation

Client HTTP / HTTPS→Kong Gateway→HTTPRoute→Services V1/V2→Pods

Le contrôleur Kong Ingress Controller lit GatewayClass, Gateway et HTTPRoute puis programme le proxy Kong. Le TP 2 termine TLS sur Kong, le TP 3 partage le trafic entre deux backends, le TP 4 observe le proxy.

Mode laboratoire : certificats autosignés, port-forward local, chart Helm installé en mode unmanaged. Pour la production, utiliser une PKI reconnue, des règles réseau et une configuration de métriques adaptée. Le ServiceMonitor du TP 4 suppose kube-prometheus-stack et demande de vérifier les labels de l'installation.
TRAVAUX PRATIQUES 01

HTTPRoute : publier Hello Kubernetes

Installer Kong, créer GatewayClass, Gateway, Deployment, Service et HTTPRoute.

Objectifs

Comprendre le plan de contrôle Kong Ingress Controller, le proxy Kong et la relation Gateway → HTTPRoute → Service → Pods. Prérequis : kubectl, Helm, cluster accessible et droits sur les namespaces.

Installer les CRD Gateway API avant Kong

kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.6.1/standard-install.yaml
kubectl get crd | grep gateway.networking.k8s.io

Installer Kong via Helm

helm repo add kong https://charts.konghq.com
helm repo update
helm install kong kong/ingress -n kong --create-namespace --wait --timeout 10m
kubectl get pods,svc,deploy -n kong

Déclarer le contrôleur

Fichier 01-gatewayclass.yaml :

apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: kong
  annotations:
    konghq.com/gatewayclass-unmanaged: "true"
spec:
  controllerName: konghq.com/kic-gateway-controller

Créer le listener HTTP

Fichier 02-gateway.yaml :

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: kong-gateway
  namespace: kong
spec:
  gatewayClassName: kong
  listeners:
  - name: http
    protocol: HTTP
    port: 80
    allowedRoutes:
      namespaces:
        from: All

Appliquer la GatewayClass et la Gateway

kubectl apply -f 01-gatewayclass.yaml
kubectl apply -f 02-gateway.yaml
kubectl get gatewayclass
kubectl get gateway -n kong

Créer les Pods V1 et leur Service

Fichier 03-app-v1.yaml :

apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-v1
  namespace: demo
spec:
  replicas: 2
  selector:
    matchLabels: {app: hello, version: v1}
  template:
    metadata:
      labels: {app: hello, version: v1}
    spec:
      containers:
      - name: hello
        image: hashicorp/http-echo:1.0.0
        args: ["-text=Hello Kubernetes V1 via Kong!", "-listen=:5678"]
        ports: [{containerPort: 5678}]
        readinessProbe:
          tcpSocket: {port: 5678}
          periodSeconds: 5
        resources:
          requests: {cpu: 25m, memory: 32Mi}
          limits: {cpu: 100m, memory: 64Mi}
---
apiVersion: v1
kind: Service
metadata:
  name: hello-v1
  namespace: demo
spec:
  selector: {app: hello, version: v1}
  ports: [{port: 80, targetPort: 5678}]

Créer le routage HTTP

Fichier 04-route-http.yaml :

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: hello-route
  namespace: demo
spec:
  parentRefs:
  - name: kong-gateway
    namespace: kong
    sectionName: http
  hostnames: ["hello.example.local"]
  rules:
  - matches:
    - path: {type: PathPrefix, value: /}
    backendRefs:
    - name: hello-v1
      port: 80

Déployer et vérifier

kubectl create namespace demo --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -f 03-app-v1.yaml
kubectl apply -f 04-route-http.yaml
kubectl rollout status deployment/hello-v1 -n demo
kubectl describe httproute hello-route -n demo

Tester via port-forward (terminal 1 et terminal 2)

kubectl port-forward -n kong svc/kong-gateway-proxy 8080:80
# Dans un autre terminal :
curl -i -H "Host: hello.example.local" http://127.0.0.1:8080/

Validation

Attendu : HTTP 200 et « Hello Kubernetes V1 via Kong! ». Test négatif : utiliser un Host inconnu et vérifier le 404. Si le Service proxy porte un autre nom, le retrouver avec kubectl get svc -n kong.

TRAVAUX PRATIQUES 02

HTTPS : TLS Termination

Chiffrer le trafic client → Kong, puis router en HTTP vers le Service V1.

Comprendre la terminaison TLS

Le Secret TLS est dans le namespace de la Gateway (kong). Kong présente le certificat, déchiffre HTTPS, puis contacte le backend HTTP. Le certificat autosigné convient uniquement à la formation.

Créer un certificat avec SAN

openssl req -x509 -nodes -newkey rsa:2048 -days 30 -keyout hello.key -out hello.crt -subj "/CN=hello.example.local" -addext "subjectAltName=DNS:hello.example.local"
kubectl create secret tls hello-tls -n kong --cert=hello.crt --key=hello.key

Ajouter un listener HTTPS à la Gateway

Fichier 05-gateway-https.yaml :

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: kong-gateway
  namespace: kong
spec:
  gatewayClassName: kong
  listeners:
  - name: http
    protocol: HTTP
    port: 80
    allowedRoutes:
      namespaces: {from: All}
  - name: https
    hostname: hello.example.local
    protocol: HTTPS
    port: 443
    tls:
      mode: Terminate
      certificateRefs:
      - kind: Secret
        name: hello-tls
    allowedRoutes:
      namespaces: {from: All}

Attacher la HTTPRoute au listener HTTPS

Fichier 06-route-https.yaml :

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: hello-route
  namespace: demo
spec:
  parentRefs:
  - name: kong-gateway
    namespace: kong
    sectionName: https
  hostnames: ["hello.example.local"]
  rules:
  - matches:
    - path: {type: PathPrefix, value: /}
    backendRefs:
    - name: hello-v1
      port: 80

Appliquer les modifications

kubectl apply -f 05-gateway-https.yaml
kubectl apply -f 06-route-https.yaml
kubectl describe gateway kong-gateway -n kong
kubectl describe httproute hello-route -n demo

Tester TLS via port-forward

kubectl port-forward -n kong svc/kong-gateway-proxy 8443:443
# Autre terminal :
curl -kiv --resolve hello.example.local:8443:127.0.0.1 https://hello.example.local:8443/
openssl x509 -in hello.crt -noout -subject -dates

Validation

Attendu : HTTP 200 avec V1, certificat présenté par Kong. L’option -k ignore la validation du certificat autosigné : ne pas l’utiliser comme solution de production. Vérifier que le port 443 est exposé par le Service Kong.

TRAVAUX PRATIQUES 03

Canary : répartir le trafic V1 / V2

Faire évoluer progressivement une application sans remplacer brutalement tous les utilisateurs.

Déployer une version V2 indépendante

Fichier 07-app-v2.yaml :

apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-v2
  namespace: demo
spec:
  replicas: 2
  selector:
    matchLabels: {app: hello, version: v2}
  template:
    metadata:
      labels: {app: hello, version: v2}
    spec:
      containers:
      - name: hello
        image: hashicorp/http-echo:1.0.0
        args: ["-text=Hello Kubernetes V2 via Kong!", "-listen=:5678"]
        ports: [{containerPort: 5678}]
        readinessProbe:
          tcpSocket: {port: 5678}
          periodSeconds: 5
        resources:
          requests: {cpu: 25m, memory: 32Mi}
          limits: {cpu: 100m, memory: 64Mi}
---
apiVersion: v1
kind: Service
metadata:
  name: hello-v2
  namespace: demo
spec:
  selector: {app: hello, version: v2}
  ports: [{port: 80, targetPort: 5678}]

Activer V2

kubectl apply -f 07-app-v2.yaml
kubectl rollout status deployment/hello-v2 -n demo
kubectl get endpointslices -n demo

Configurer les poids 90 % / 10 %

Fichier 08-route-canary.yaml :

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: hello-route
  namespace: demo
spec:
  parentRefs:
  - name: kong-gateway
    namespace: kong
    sectionName: https
  hostnames: ["hello.example.local"]
  rules:
  - matches:
    - path: {type: PathPrefix, value: /}
    backendRefs:
    - name: hello-v1
      port: 80
      weight: 90
    - name: hello-v2
      port: 80
      weight: 10

Appliquer la route canary

kubectl apply -f 08-route-canary.yaml
kubectl describe httproute hello-route -n demo

Exécuter 100 requêtes et compter les réponses

for i in $(seq 1 100); do curl -ks --resolve hello.example.local:8443:127.0.0.1 https://hello.example.local:8443/; done | sort | uniq -c

Interprétation

Les proportions sont statistiques et peuvent fluctuer. Pour un rollback immédiat, remplacer les poids par V1=100, V2=0 puis réappliquer. Pour une montée progressive, essayer 90/10 → 75/25 → 50/50 → 0/100 après validation des métriques.

TRAVAUX PRATIQUES 04

Observabilité : Prometheus et Grafana

Suivre le volume de requêtes, les erreurs, la latence et la santé du routage.

Prérequis et architecture

Ce chapitre suppose kube-prometheus-stack déjà installé et ses CRD ServiceMonitor disponibles. Les métriques du contrôleur KIC et celles du proxy Kong sont distinctes. Pour les requêtes HTTP, activer le plugin Prometheus de Kong Gateway. Vérifier les noms des Services et labels Helm avant de créer un ServiceMonitor.

Activer le plugin Prometheus global

Fichier 09-kong-prometheus-plugin.yaml :

apiVersion: configuration.konghq.com/v1
kind: KongClusterPlugin
metadata:
  name: prometheus
  annotations:
    kubernetes.io/ingress.class: kong
  labels:
    global: "true"
plugin: prometheus
config:
  per_consumer: false
  status_code_metrics: true
  latency_metrics: true
  bandwidth_metrics: true
  upstream_health_metrics: true

Vérifier les CRD et appliquer le plugin

kubectl get crd kongclusterplugins.configuration.konghq.com
kubectl apply -f 09-kong-prometheus-plugin.yaml
kubectl get kongclusterplugin prometheus

Exposer les métriques du Data Plane

La configuration Kong doit activer un listener status/metrics sur 0.0.0.0:8100. Dans un lab DB-less, appliquer cette option au chart via Helm (voir commandes suivantes), puis vérifier la présence du port 8100. Ce port doit rester interne au cluster.

Activer le listener status Kong (chart Helm)

helm upgrade kong kong/ingress -n kong --reuse-values --set gateway.env.status_listen="0.0.0.0:8100" --wait
kubectl get pods -n kong
kubectl get deploy -n kong --show-labels

Service interne de métriques : vérifier le selector

Fichier 10-kong-metrics-service.yaml :

apiVersion: v1
kind: Service
metadata:
  name: kong-prometheus-metrics
  namespace: kong
  labels:
    app.kubernetes.io/name: kong-prometheus-metrics
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: gateway
  ports:
  - name: metrics
    port: 8100
    targetPort: 8100

Trouver les labels réels du proxy

kubectl get pods -n kong --show-labels
# Adapter spec.selector de 10-kong-metrics-service.yaml au pod Gateway.
kubectl apply -f 10-kong-metrics-service.yaml
kubectl get endpointslices -n kong -l kubernetes.io/service-name=kong-prometheus-metrics

Tester les métriques avant Prometheus

kubectl port-forward -n kong svc/kong-prometheus-metrics 8100:8100
# Dans un autre terminal :
curl -s http://127.0.0.1:8100/metrics | head -30

Créer le ServiceMonitor

Fichier 11-servicemonitor.yaml :

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: kong-prometheus
  namespace: kong
  labels:
    release: kube-prometheus-stack
spec:
  namespaceSelector:
    matchNames: [kong]
  selector:
    matchLabels:
      app.kubernetes.io/name: kong-prometheus-metrics
  endpoints:
  - port: metrics
    path: /metrics
    interval: 30s

Appliquer et contrôler la découverte

kubectl get crd servicemonitors.monitoring.coreos.com
# Adapter metadata.labels.release selon le sélecteur du Prometheus installé.
kubectl apply -f 11-servicemonitor.yaml
kubectl get servicemonitor -n kong
# Dans Prometheus : Status > Targets, vérifier la cible kong-prometheus.

Générer du trafic pour remplir les métriques

for i in $(seq 1 300); do curl -ks --resolve hello.example.local:8443:127.0.0.1 https://hello.example.local:8443/ >/dev/null; done

Exemples de requêtes PromQL (adapter les labels et noms exposés)

sum(rate(kong_http_requests_total[5m]))
sum by (code) (rate(kong_http_requests_total[5m]))
sum(rate(kong_http_requests_total{code=~"5.."}[5m])) / clamp_min(sum(rate(kong_http_requests_total[5m])), 0.001)
# Explorer les métriques réellement disponibles via /metrics :
# kong_latency_ms_bucket, kong_kong_latency_ms_bucket, etc. selon la version/plugin.

Tableau de bord et alertes

Dans Grafana : datasource Prometheus, panneaux RPS, 4xx/5xx, taux 5xx, latence p95 si histogrammes disponibles. Ajouter une alerte lorsque le ratio 5xx dépasse 5 % pendant 5 minutes, et une alerte « cible absente ». Les noms exacts des métriques et leur granularité varient selon les versions Kong et les options du plugin.
